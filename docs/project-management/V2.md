# 项目管理 V2

状态：需求探索  
最后更新：2026-08-25

V2 的目标不是重做 V1，而是在已有立项、计划和执行能力上建立可比较、可变更、可验收、可关闭的项目控制闭环。

## 进入 V2 的前提

- V1 主流程按 `V1_ACCEPTANCE.md` 验收完成。
- V1 的 P0 缺陷已经关闭。
- 项目状态、任务状态、交付状态和权限边界有稳定测试保护。
- 当前数据库结构能够可靠部署，不再依赖未知历史脚本组合。

## V2 首要问题

项目启动后计划被冻结，但当前系统提示“执行中调整请走项目变更”时，并没有真正的变更流程。V2 首先需要补齐：

```text
批准计划
  → 发布基线
  → 执行并识别偏差
  → 提交变更
  → 分析和审批
  → 受控应用
  → 形成新基线
  → 工作包验收
  → 项目关闭
```

## 建议范围

### V2.0：计划基线与变更

- 项目启动时形成第一版不可修改的计划基线。
- 基线保存项目日期、WBS、工作包、任务、正式交付要求、预计工时和预算快照。
- 当前计划可以与历史基线比较。
- 执行中通过变更申请调整冻结内容，禁止绕过变更直接编辑。
- 变更记录原因、影响对象以及日期、人员、工时、预算和交付差异。
- 变更支持草稿、提交、批准、退回、撤回和应用。
- 批准与应用分离；应用必须保持事务一致性。
- 变更应用成功后形成新基线并保留审计链。

### V2.1：工作包验收与项目关闭

- 任务和交付物满足条件后，工作包进入待验收。
- 验收记录包含验收人、结论、意见、时间和证据。
- 项目关闭前检查工作包、交付物、问题、遗留事项和复盘材料。
- 关闭后项目归档只读，保留完整查询和审计能力。

### 后续候选项

- 任务依赖、循环校验、甘特图和关键路径
- 计划进度、实际进度和基线偏差
- 工时填报与按工时加权的进度聚合
- 风险登记册、风险转问题、问题逾期和升级
- 预算与实际成本
- 项目健康度、模板、跨项目资源和项目组合

这些候选项不自动进入 V2.0；只有确定用户、价值、规则和验收条件后才排期。

## 必须先决定的问题

1. 谁可以创建、审批和应用项目变更？
2. 是否允许紧急变更先执行后补审批？
3. 启动时是否自动发布第一版基线？
4. 新基线是否只能由批准的变更产生？
5. 一个项目能否同时存在多个有效基线？
6. 项目“执行完成”和“正式关闭”是否分成两个状态？
7. 工作包验收人能否与工作包负责人相同？
8. 哪些未关闭问题允许作为遗留事项进入项目关闭？
9. 首版进度按任务数、预计工时还是人工填报计算？
10. V2 是否管理实际成本，还是只做计划预算和变更金额？

## V2 功能的准入条件

每个主题进入开发前，至少在本文件或一份短专题文档中写清：

- 解决哪个用户的什么问题
- 流程和状态如何变化
- 谁能看、谁能操作
- 哪些数据被冻结，哪些允许修改
- 失败、撤回、并发和重复操作如何处理
- 数据如何从 V1 迁移
- 用哪些场景判断完成

没有验收条件的功能不进入开发。专题稳定后，把最终范围和结论收回本文件；过程性讨论不长期保留。
