# 项目管理系统 UI / 布局专项审计（2026-09-04）

## 1. 结论

结论：**当前常规桌面宽度下，多数列表页可用；采购明细类页面存在确定性的严重布局缺陷，项目管理中的多张宽表也缺少稳定的窄屏策略，暂不能认为 UI 已完成正式验收。**

本轮共登记 9 项 UI 问题：

- P1：1 项；
- P2：7 项；
- P3：1 项。

最高风险是 `PM-UI-006`：采购入库详情在固定 760px 抽屉中直接放入 14 列明细，到货详情则为 15 列；表格没有横向滚动、列宽、固定列或长文本策略。用户提供的截图问题已在本地 Chrome 复现，中文表头、项目名和成本类别被压成逐字竖排，无法高效、可靠地完成单据核对。

本轮只做审计、登记和修复建议，没有开始全局样式改造，也没有新增、修改或提交业务单据。

## 3. 判定标准

本轮采用以下最小 UI 验收标准：

1. 中文标签、表头和字段值不得因容器过窄而形成逐字竖排。
2. 明细表达到 10 列或逻辑总宽超过容器时，必须明确配置最小列宽和可发现的横向滚动。
3. 编码、日期、数量、单价、金额、状态等短字段原则上不换行；项目名、物料名、说明等长字段使用合理宽度、最多两行，或省略加 Tooltip/展开查看。
4. 窄抽屉不得承载需要横向比对的 14–16 列业务核对表；应使用 80–96vw 宽抽屉、全屏弹窗或独立详情页。
5. 固定操作列内的主要动作不应被挤成单字或多行；动作较多时保留主要动作，其余放入“更多”。
6. 左树右表、左右分栏应依据组件实际可用宽度切换布局，而不是只看全局窗口宽度。
7. 金额在同一页面应统一货币符号、千分位和两位小数。
8. 正式回归至少覆盖 1920×1080、1440×900、1366×768，以及 125% 浏览器缩放和超长中文/英文测试数据。

## 5. 正式问题

### PM-UI-006：采购入库/到货详情在窄抽屉内逐字换行

- 类型：UI
- 优先级：P1
- 状态：新发现
- 角色：采购专员、成本管理员、项目负责人

实际表现：

- 入库详情 14 列、到货详情 15 列被塞进固定 760px 抽屉。
- 表头出现“成/本/类/别”“入/库/数/量”等逐字换行。
- 项目名、成本类别、来源单号、物料编码、仓库和批次号同时被压窄，行高异常增大，跨列核对非常困难。
- 本地 Chrome 已复现用户截图中的同一问题；不是单条数据偶然过长，也不是截图缩放导致。

静态依据：

- `Frontend/src/views/mes/purchase/inbound.vue:129` 固定 `width="760px"`；`:141-148` 的明细表未配置横向滚动；`:250-265` 共 14 列且没有明确列宽、ellipsis 或 fixed。
- `Frontend/src/views/mes/purchase/receipt.vue:189` 固定 760px；`:205-212` 明细表无横向滚动；`:390-406` 共 15 列且没有宽度保护。

业务影响：采购人员难以确认“哪个项目、哪个成本类别、哪种物料、什么数量和金额”是否一致，也不利于成本管理员追查采购入库实际成本。错误核对可能直接影响库存和项目成本。

建议：

1. 桌面端改为约 92vw、最大 1500–1600px 的宽抽屉，或全屏/独立详情；移动端全屏。
2. 入库表设置约 1850–2000px、到货表约 1900–2050px 的逻辑宽度并启用 `scroll.x` 和 sticky 横向滚动条。
3. 来源单号、编码、日期、数量、价格、金额、仓库、库位、单位禁止换行。
4. 项目、成本类别和物料名称使用省略加 Tooltip，或允许受控的最多两行。
5. 固定来源单号/物料编码等识别列；数量、单价、金额右对齐。
6. 若不希望默认展示全部列，可只展示核对必需列，其余放入行展开区。

回归条件：三种目标分辨率和 125% 缩放下，所有表头均保持横向可读；横向滚动条可发现；任意一行可以连续核对项目、成本类别、物料、数量和金额。

### PM-UI-007：采购新增/编辑和参照弹窗的交互字段被挤压

- 类型：UI
- 优先级：P2
- 状态：新发现

实际表现：本地打开“新增入库单”后，980px 弹窗内的 16 列表格即使没有数据，前部表头也已经逐字换行。载入仓库、库位、批次和日期输入控件后，可操作空间会进一步减少。

静态依据：

- `inbound.vue:66-70,97-126,267-284`：固定 980px 编辑弹窗、16 列、无横向滚动。
- `receipt.vue:88-92,139-185,408-423`：固定 980px 编辑弹窗、14 列、无横向滚动。
- `inbound.vue:151-181,286-300`：1100px 参照弹窗内 13 列，无明确宽度和横向滚动。
- `receipt.vue:216-252,425-435`：1100px 参照弹窗内 9 列，无稳定宽度策略。
- `inbound.vue:478-482`、`receipt.vue:679-683` 的筛选栏只使用 flex，没有换行策略。

建议：编辑场景使用约 96vw 或全屏弹窗；表格逻辑宽度分别按约 2200px/1900px 设置；固定物料识别列和操作列。窄屏时筛选栏允许换行。采购订单编辑页已有 96% 弹窗和横向滚动，可作为改造参考。

### PM-UI-008：项目预算执行和实际成本宽表缺少稳定窄屏策略

- 类型：UI
- 优先级：P2
- 状态：新发现

实际表现：1829×920 下主要数字仍可读，但实际成本的来源和事由已经出现明显截断，表格底部没有横向滚动；当有效宽度降低时，列只能继续压缩。

静态依据：

- `Frontend/src/components/projectManagement/ProjectBudgetManager.vue:89-94,512-522`：预算执行表 9 列，已声明列宽合计约 1240px，成本类别列还未定宽，但表格没有 `scroll.x`。
- `ProjectBudgetManager.vue:289-335,530-540`：实际成本 10 列，已声明宽度约 1030px，另有成本类别和事由两个长文本列，同样没有横向滚动。
- 来源单据使用组合单元格，信息密度更高；自定义渲染也绕开了通用表格的默认省略保护。

建议：预算执行设置 `scroll.x >= 1380`，实际成本设置 `scroll.x >= 1360`；固定成本类别/日期与金额/操作等关键列；来源和事由使用统一省略 Tooltip，并提供可点击下钻。

## 6. 共性根因

1. 多个业务页直接使用原生 `a-table`，没有沿用通用列表组件的列宽、ellipsis 和横向滚动保护。
2. 抽屉/弹窗使用固定像素宽度，却没有同时定义内部表格的逻辑宽度。
3. 部分 `scroll.x` 是手写经验值，小于列宽真实合计，配置存在但不能发挥保护作用。
4. 页面主要根据全局 viewport 做响应式，忽略侧栏、树面板、抽屉和左右分栏后的实际容器宽度。
5. 自定义 `bodyCell` 绕开了 `BearJiaProTable` 已有的省略和 Tooltip 行为。
6. 缺少统一的金额格式器、宽表规范和带长文本的视觉回归数据。

## 7. 建议的组件级改造

建议先建立统一规则，再逐页迁移：

1. 封装采购/成本宽表规范：按字段类型提供默认宽度、对齐、nowrap、ellipsis、Tooltip 和 fixed 配置。
2. 提供统一 `EllipsisText`，供自定义单元格复用，支持单行/两行、省略提示和复制。
3. 封装 `ResponsiveDetailSurface`：根据列数和内容自动选择普通抽屉、宽抽屉或全屏详情。
4. 用列宽合计生成 `scroll.x`，避免手写小于真实宽度的数值。
5. 对左右分栏使用容器宽度或 `ResizeObserver` 决定堆叠，不只依赖窗口媒体查询。
6. 统一人民币、日期、数量和单价格式，短数值列右对齐且不换行。
