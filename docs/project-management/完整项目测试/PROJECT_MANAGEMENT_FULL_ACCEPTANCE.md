## 1. 测试目标

使用一个贴近真实制造业研发过程的完整项目，从基础数据准备开始，贯穿立项、审批、项目启动、执行、变更、预算与成本、工时、交付和项目完成，验证：

1. 当前项目管理模块已经提供的功能能够形成完整业务闭环。
2. 页面展示、交互顺序、字段命名和操作入口符合真实项目人员的使用习惯。
3. 页面按钮、接口权限和服务层业务权限保持一致，管理员不成为业务越权特例。
4. 状态、金额、日期、人员、附件、审批快照、基线和审计数据前后一致。
5. 采购入库成本与工时人工成本能够正确进入项目预算执行统计。
6. 对缺失功能、业务断层、界面问题和程序缺陷形成独立问题清单，完成首轮全量测试后统一修复并回归。

本文件是本轮测试的执行主清单，不覆盖已有专项 PRD 和验收文档。专项文档用于说明规则，本文件用于证明整套系统在真实流程中是否可用。

## 2. 测试执行原则

- 以 Chrome 中的真实页面操作为主，同时检查浏览器控制台、网络请求、后端日志和数据库最终结果。
- 每条用例填写“实际结果、状态、问题编号”；不得仅凭接口返回成功判断页面验收通过。
- 页面隐藏按钮不能替代后端校验。关键越权、状态绕过和非法数据必须直接调用接口复核。
- 测试中发现的问题立即登记到独立问题文档，不在本验收表中写长篇分析。
- 首轮测试期间原则上不边测边改，避免测试基线不断变化。只有导致后续主流程无法继续的 P0 阻断问题，才允许先登记、修复、回归该节点后继续。
- 首轮全部完成后，对问题清单统一评审、修复；修复完成后执行受影响模块回归和关键主链路回归。
- 所有业务时间按 `Asia/Shanghai` 展示，日期时间期望格式为 `YYYY-MM-DD HH:mm:ss`，不得因浏览器或服务时区产生 8 小时偏差。

### 3.1 采购集成边界

采购模块不做全模块验收，只验证与项目管理直接相关的链路：

```text
采购订单行选择项目和成本类别
  → 到货单继承且只读
  → 入库单继承且只读
  → 审核入库后按入库明细形成项目实际成本
  → 项目及工作包预算执行更新
  → 退回、弃审或冲销后的成本处理正确
```

采购价格、税率、供应商、库存等通用采购能力只验证其不被项目字段改造破坏，不展开为采购模块的完整验收。

## 6. 完整业务执行顺序

本轮必须按以下顺序形成一条真实主链，专项反例在对应节点穿插执行：

1. 核查菜单、角色、基础数据和四类审批流程。
2. 由申请人创建项目草稿，完成立项信息、拟定团队、WBS 概要、分类预算和附件。
3. 保存草稿、提交立项；审批人查看结构化审批内容并执行驳回重提、最终通过。
4. 在待启动状态完善正式团队、WBS、工作包、任务和正式交付要求。
5. 在待启动状态完成项目分类预算到工作包的初始分配，核对“已分配至工作包预算”和“待分配”口径。
6. 执行启动前检查，修正所有问题后启动项目，确认生成 V1 基线。
7. 验证启动后计划冻结，通过项目变更完成基础信息、WBS、任务、团队、交付物、项目预算和工作包预算调整。
8. 执行任务生命周期、任务成果和问题处理。
9. 执行采购订单、到货、入库，核对材料实际成本及预算执行。
10. 填报并审批项目工时，核对任务实际工时和内部人工成本；再验证归档工时更正和冲销。
11. 提交并审批全部必交交付物，处理全部未完成任务和未关闭问题。
12. 完成项目，验证完成后的只读、历史、基线、成本和审计追溯。
13. 使用各角色和非项目成员复核数据范围，执行界面、时区、附件和构建回归。

## 8. 每个页面的设计复核要求

功能通过不代表页面设计通过。每打开一个页面、弹窗、抽屉或详情页，同时检查：

1. 当前页面能否让用户在 5 秒内知道“是什么、现在什么状态、下一步做什么”。
2. 主操作是否突出，次要操作是否收敛，危险操作是否有确认。
3. 字段顺序是否符合业务填写顺序，而不是数据库字段顺序。
4. 状态名称是否表达业务动作，如“问题已解决”优于单纯展示状态码变化。
5. 原值、新值、金额、时间、人员、附件是否使用用户可读格式，禁止展示原始 JSON。
6. 表格列宽、抽屉宽度、页签和滚动是否保证重要信息完整。
7. 空状态是否告诉用户为什么为空，以及可以去哪里完成前置配置。
8. 禁用按钮是否有原因说明；无权限操作不能只靠“点了以后 403”。
9. 下拉是否支持搜索，候选范围是否准确，已停用或跨项目对象不得混入。
10. 页面是否存在真实业务断层，例如创建工作包后还要反复退出、重新定位才能配置交付物。

任何不满足项都登记到 `PROJECT_MANAGEMENT_TEST_FINDINGS.md`，即使接口和数据结果正确。

## 9. 测试产物与完成标准

首轮测试必须产出：

- 本文档中所有适用用例的实际结果和状态。
- 每个失败或阻塞项对应的问题编号。
- 关键流程截图或录屏、失败请求、后端错误日志和必要数据库证据。
- 独立的问题、界面优化和业务合理性清单。
- 首轮总结：通过数、失败数、阻塞数、不适用数及主要风险。

进入统一修复前的条件：

- 所有可执行用例已经跑完；不能执行的用例有明确阻塞原因。

- 业务规则问题与纯程序缺陷分开，避免未经确认直接改变业务逻辑。

最终验收通过条件：

- 前后端格式化、检查和生产构建通过。
