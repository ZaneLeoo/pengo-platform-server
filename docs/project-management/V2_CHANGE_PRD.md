# V2.0 计划基线与变更 PRD

状态：开发中，待验收  
最后更新：2026-08-26  
所属版本：[项目管理 V2](V2.md)

## 1. 目标与边界

项目启动后，计划不再允许通过日常编辑被悄然修改。项目成员应能提出计划调整，审批人能清楚判断变更前后差异，项目负责人能在确认后将已批准的变更受控落地，并留下可比较的计划版本。

本专题解决的是“计划承诺如何受控改变”，不负责变更后的实际执行任务分派或二次生效审批。

### 1.1 术语

| 术语 | 定义 |
| --- | --- |
| 基线 | 某一时刻已确认计划的不可变快照，用于比较和追溯。 |
| 当前计划 | 当前正在执行的、可由已应用变更生成的最新计划。 |
| 变更单 | 对一个项目当前基线提出的成组调整申请。 |
| 变更项 | 变更单中的单条新增、修改或删除操作。 |
| 审批 | 对变更内容是否允许执行的业务决定，由 `PLAN_CHANGE` 审批流完成。 |
| 确认应用 | 项目负责人将已审批变更原子写入当前计划的落地动作，不是第二次审批。 |
| 基线冲突 | 变更单引用的基线已不是当前基线，不能再直接应用。 |

### 1.2 不在本期范围

- 存量项目数据迁移、补建基线或兼容历史项目。
- 紧急变更先执行、后补审批。
- 变更任务中心、变更执行人待办、第二套“生效审批”。
- 已有 WBS、工作包或任务跨父级移动。
- 已应用变更的回滚；后续调整必须新建变更单。
- 任务依赖、关键路径、甘特图、实际成本和工时核算。

## 2. 适用项目与计划冻结

### 2.1 项目状态规则

| 项目状态 | 计划编辑 | 可发起变更 | 基线规则 |
| --- | --- | --- | --- |
| 立项审批中 / 已退回 | 按现有立项规则 | 否 | 无基线 |
| 待启动 | 允许直接完善计划 | 否 | 无基线 |
| 执行中 | 受控字段禁止日常编辑 | 是 | 启动时自动生成 V1 |
| 暂停中 | 受控字段禁止日常编辑 | 是 | 沿用当前基线 |
| 已完成 / 已终止 | 只读 | 否 | 仅查询历史 |

项目启动成功时，系统自动创建 `V1` 基线。V2 项目从该时点进入计划受控状态。受控范围包括项目计划字段、WBS、工作包、任务、项目团队和正式交付物要求。

## 3. 用户、权限与数据范围

| 角色 | 权限 |
| --- | --- |
| 项目活动成员 | 查看本项目基线、变更单和差异；创建、编辑、提交、撤回自己的草稿或退回单。 |
| 变更发起人 | 查看本人变更单的全部审批、附件和应用记录；审批退回后可修改并重新提交。 |
| 审批人 | 在统一审批中心查看业务快照、完整差异和附件，并按流程同意或驳回。 |
| 项目负责人 | 查看本项目全部变更；对审批通过且基线一致的变更确认应用。 |
| 非项目成员（且未作为发起人或审批参与人） | 无权查询项目基线、变更单、附件或审批业务快照。 |

权限由后端独立校验。`admin` 不作为项目变更的业务特例，不得绕过成员、审批或负责人应用规则。

## 4. 业务流程与状态机

```text
发起人保存草稿
  → 提交审批
  → 审批中
      ├─ 任一节点驳回 → 已退回 → 发起人修改后重新提交
      └─ 全部节点通过 → 待应用
                              ├─ 项目负责人确认应用 → 已应用 + 创建下一版基线
                              └─ 当前基线已变化 → 需重新核对 → 发起人修改后重新提交

草稿 / 已退回 / 审批中（未结束） → 发起人撤回 → 已撤回
```

### 4.1 状态定义

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| 草稿 | 尚未进入审批 | 编辑、删除、提交 |
| 审批中 | 已创建审批实例 | 查看；发起人可撤回 |
| 已退回 | 审批被驳回 | 发起人编辑、重新提交、删除 |
| 待应用 | 审批已通过，尚未写入当前计划 | 项目负责人确认应用；全员查看 |
| 需重新核对 | 审批期间当前基线已变化 | 发起人核对、修改并重新提交 |
| 已应用 | 已更新当前计划并生成新基线 | 只读查询 |
| 已撤回 | 发起人主动结束 | 只读查询 |

审批驳回意见、每次重新提交的审批实例、审批人和处理时间必须保留。重新提交创建新的流程实例，不覆盖旧实例。

## 5. 变更单设计

### 5.1 基本信息

| 字段 | 规则 |
| --- | --- |
| 变更单编号 | 系统生成，项目内唯一。 |
| 标题 | 必填，简明描述本次变更。 |
| 项目 | 创建时固定，不允许跨项目调整。 |
| 引用基线版本 | 创建草稿时固定为当前基线版本。 |
| 变更原因 | 必填，说明触发原因。 |
| 影响说明 | 必填，说明进度、范围、资源、预算或交付影响；未影响时填写“无”。 |
| 附件 | 可选，多文件；通过统一下载接口访问，不直接暴露存储路径。 |
| 发起人、创建时间、提交时间 | 系统记录，只读。 |

### 5.2 变更清单

一张变更单可包含多条变更项。每一项必须明确模块、操作类型、目标对象、变更前值、变更后值和变更原因。审批详情按模块分组展示，并用“原值 → 新值”突出差异。

| 模块 | 支持操作 | 规则 |
| --- | --- | --- |
| 项目计划 | 修改 | 项目计划开始/结束日期、计划预算及受控计划说明。项目名称、立项申请原始内容不属于本专题。 |
| WBS | 新增、修改、受限删除 | 可维护名称、范围说明、负责人、计划日期、预计工时和预算等受控字段。 |
| 工作包 / 任务 | 新增、修改、受限删除 | 可维护名称、负责人、计划日期、预计工时、预算、计划说明等受控字段。 |
| 项目团队 | 新增、修改、受限删除 | 可增加或移除活动成员、调整项目角色；不影响已启动审批实例的候选人快照。 |
| 正式交付物要求 | 新增、修改、受限删除 | 可维护名称、类型、负责人、计划交付日期、是否需要审批和验收要求。 |

### 5.3 删除限制

删除只允许目标节点没有不可丢失业务记录。出现下列任一情况时，系统拒绝删除并说明原因：

- 存在子 WBS、工作包或任务；
- 存在交付物提交或审核记录；
- 存在问题、活动记录或工时记录；
- 已完成、已终止或其他不可逆执行记录。

已有记录的计划只能通过后续计划调整或停止后续执行处理，不能用删除抹除历史。

## 6. 审批与确认应用

### 6.1 审批流

- 变更提交使用已发布的 `PLAN_CHANGE` 流程模板。
- 审批节点支持指定用户和项目角色；角色节点有多名候选人时，任一候选人处理即完成该节点。
- 发起人自动从全部审批候选人中排除；排除后节点无候选人时，禁止提交并提示配置问题。
- 流程模板是否包含项目负责人节点由流程配置决定；无论模板配置如何，项目负责人仍负责最终确认应用。
- 未配置已发布流程时，变更单只能保存草稿，不能提交。

### 6.2 确认应用

审批通过只表示允许变更，不修改当前计划。项目负责人在变更详情中查看批准内容、审批记录、附件与差异后点击“确认应用”。

应用时系统必须在同一事务内完成：

1. 锁定项目及当前基线，校验变更单引用基线仍为当前版本；
2. 重新校验项目状态、负责人身份、变更项完整性及删除限制；
3. 按变更清单更新当前计划；
4. 创建下一版不可变基线，关联本次变更单；
5. 写入应用人、应用时间和操作审计，并将变更单置为“已应用”。

任一校验或写入失败时，事务整体回滚，当前计划与基线保持不变。若当前基线已变化，变更单转为“需重新核对”，不得覆盖新计划。

## 7. 页面与查询

### 7.1 项目计划页

项目计划区域增加“基线与变更”入口，包含：

- 当前基线卡片：版本、生成时间、来源变更单；
- 基线历史：版本列表、快照摘要、创建人、创建时间；
- 基线比较：选择两版后按模块展示新增、修改、删除差异；
- 变更单列表：编号、标题、发起人、引用基线、状态、审批状态、创建/提交/应用时间；
- “发起变更”入口：仅在执行中、暂停中且当前用户具备创建能力时显示。

### 7.2 变更详情

详情展示基本信息、变更清单、附件、审批流程和应用记录。不同状态只展示当前用户具有权限的动作，前端以服务端返回的能力字段为准。

统一审批中心打开变更审批时，必须展示业务专属只读详情及完整差异，而不是通用 JSON 内容。

## 8. 接口与审计要求

- 基线查询、比较、变更单 CRUD、提交/撤回、详情、附件、确认应用等接口均校验项目数据范围。
- 列表与详情返回操作能力字段，至少包括创建、编辑、删除、提交、撤回、重新提交、确认应用及只读原因。
- 附件接口只保存受控文件引用和显示名称；下载通过统一资源下载接口，并校验项目数据权限。
- 审计记录覆盖草稿创建、编辑、提交、撤回、审批结果、重新提交、冲突、应用成功和应用失败。

## 9. 典型示例

项目当前基线为 `V1`，计划结束日期为 9 月 30 日。成员提出“新增集成测试任务并延期两周”：

1. 创建变更单，引用 `V1`，填写原因和影响说明；
2. 增加两条变更项：项目结束日期 `9 月 30 日 → 10 月 15 日`，在指定工作包下新增“集成测试”任务；
3. 上传评估文档并提交 `PLAN_CHANGE` 审批；
4. 全部审批通过后变更单进入“待应用”；
5. 项目负责人确认应用；系统写入日期和任务、创建 `V2` 基线，并保留 `V1` 与变更单审计链。
